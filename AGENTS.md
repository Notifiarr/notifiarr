# Notifiarr agent guide

## Project

Notifiarr is the unified client for Notifiarr.com. It is written in Go and Svelte and runs on most operating systems. The client runs a web server, monitors local services, sends system and Plex data to Notifiarr, and supports media requests from Discord. See `README.md` and `examples/MANUAL.md` for the user-facing scope and command-line options.

## Build and run

The module requires Go 1.27.0 (`go.mod`). Run commands from the repository root.

| Command | Purpose |
| --- | --- |
| `make generate` | Generate the API definitions and frontend assets. |
| `make notifiarr` | Build `./notifiarr`. |
| `make dev` | Generate, build a race-enabled `./notifiarr`, and run it. |
| `make release` | Clean, generate, and build release binaries and packages. It needs the packaging and signing tools used by the target platforms. |
| `make clean` | Remove generated build assets and release output. |

`make generate` runs the Go generators under `frontend/src/api` and `frontend`, and the frontend generator runs `npm install` and `npm run build`. It also creates `frontend/dist` before generation. Do not edit generated files directly; for example, `frontend/locales.go` is generated by `frontend/generate.sh`.

For a local run, use `make dev`. To build without starting the client, use `make notifiarr`. The example configuration is `examples/notifiarr.conf.example`; the manual documents `-c`/`--config` and other runtime options.

## Tests and lint

Run the complete Go test suite with `go test ./...`. The repository Makefile also provides `make test`; it cleans and generates first, runs `make lint`, then runs `go test -race -covermode=atomic ./...`.

Run `golangci-lint run` for the current platform. `make lint` additionally runs `make generate`, `codespell`, prints the linter version, and runs golangci-lint for Linux, Darwin, FreeBSD with `--build-tags nodbus`, and Windows. The linter configuration is `.golangci.yml`; it enables the `gci`, `gofmt`, `gofumpt`, and `goimports` formatters.

The frontend has its own checks in `frontend/package.json`: from `frontend`, use `npm run check`, `npm run lint`, `npm run format:check`, and `npm test`. The pull-request workflow runs those checks in `.github/workflows/frontend.yml`.

## Layout

- `main.go` is the executable entry point and starts `pkg/client`.
- `pkg/client` owns startup, the web server, handlers, GUI profile, tray commands, and embedded HTML templates.
- `pkg/apps` contains integrations for Radarr, Lidarr, Sonarr, Readarr, and Prowlarr. `pkg/apps/apppkg` contains small libraries for integrated applications without their own GitHub repositories.
- `pkg/services` implements service and network checks. `pkg/checkapp` contains application checks.
- `pkg/configfile` handles configuration files and passwords; `pkg/ui` contains platform-specific UI behavior.
- `pkg/snapshot` collects system, disk, process, RAID, SMART, NVIDIA, MySQL, and user information. `pkg/mnd` contains metrics, Prometheus support, constants, and shared types.
- `pkg/triggers` contains trigger features such as backups, commands, dashboards, file watching, gaps, Plex, snapshots, and updates. `pkg/website` handles website communication and client information.
- `pkg/bindata` embeds extra files; `pkg/cooldown`, `pkg/logs`, `pkg/private`, and `pkg/update` provide supporting functionality.
- `frontend` contains the Svelte UI, API generation, locales, tests, and build scripts. `examples`, `init`, and `userscripts` contain configuration examples, platform packaging/service files, and install scripts.

## Code conventions

Use standard Go structure and idioms. Keep errors explicit and preserve context with wrapped errors (`fmt.Errorf("...: %w", err)`) where the surrounding code does so. Use sentinel errors with `errors.Is` when the package exposes them. Follow the existing standard-library `log` usage and include useful context in server-side errors.

Run formatting and imports through the repository's configured tools. Keep generated output reproducible through `make generate`; change generator inputs or scripts instead of generated output. Respect platform build tags and test changes that affect platform-specific files.

## Commits and pull requests

Recent commits use concise, imperative descriptions and often include a GitHub PR number, for example `Update ... (#1345)`. Use the repository's existing issue prefixes when relevant: the issue forms use `Bug - ` and `FR - `. The repository has no checked-in PR template.

For a contribution, discuss a proposal in the Discord linked from `README.md`, make the change on a branch, run the relevant Go and frontend checks, and open a pull request against the appropriate repository branch on `github.com/Notifiarr/notifiarr`. Pull-request CI is configured for `main`, `unstable`, and `development`; describe the behavior change and the commands you ran in the PR.
